  # Near-MVP Architecture Hardening Plan

  ## Summary

  Evolve the current implementation into a reliable near-MVP with these locked decisions:

  - PostgreSQL is authoritative for operational workflow state.
  - Fabric asynchronously stores immutable, schema-validated proofs; it does not re-execute business commands.
  - Partial movements create child lots with explicit lineage and quantity conservation.
  - Workflow orchestration uses a versioned domain state machine, not a BPMN platform.
  - Harden the existing two-organization Fabric network; defer five-organization deployment.
  - Reset and deterministically reseed development data rather than migrating existing local transactions.
  - All critical and high findings are release blockers. Medium production concerns may be documented and deferred.

  Create three maintained documents during implementation:

  - docs/implementation/mvp-hardening-plan.md: phases, status, acceptance gates, and dependencies.
  - docs/product/assumptions-for-demo.md: explicit near-MVP limitations and operational assumptions.
  - docs/implementation/production-readiness-todos.md: deferred pilot and production work with priority and rationale.

  ## Implementation Changes

  ### Phase 0: Stabilize the Baseline

  - Complete or isolate the current feature/fabric-hardening work before architecture changes.
  - Repair Fabric contract test stubs to support composite-key APIs and make all unit tests green.
  - Prevent tests from modifying tracked journals or shared state by using per-test temporary paths.
  - Add a CI gate for build, typecheck, lint, unit tests, demo HTTP tests, and opt-in live Fabric tests.
  - Record the current database and API behavior before replacing snapshot persistence.

  Exit gate: the working tree has a reproducible green baseline, excluding explicitly opt-in Fabric integration tests.

  ### Phase 1: Establish the Fabric Proof Boundary

  - Introduce one canonical LedgerProof schema containing:
      - eventId, operationId, event type and schema version.
      - Entity type and ID.
      - Actor subject, application role, and submitting application organization.
      - Canonical payload hash and non-sensitive proof payload.
      - Business timestamp generated by the API transaction.

  - Make RecordLedgerProof the only API outbox submission path. Stop asynchronously replaying CreateCommodityLot, DispatchLot, RecordDistribution, and other business commands.
  - Make proof recording idempotent by eventId; an identical replay succeeds, while conflicting content for the same ID fails.
  - Derive all chaincode IDs and timestamps from ctx.stub.getTxID() and ctx.stub.getTxTimestamp(). Remove randomUUID(), wall-clock time, and other nondeterministic state generation from chaincode execution.
  - Retain named business transactions only as non-API compatibility functions until removed in a later version; mark them deprecated and exclude them from the gateway adapter.
  - Store the real Fabric transaction ID returned by the committed transaction and correlate it with eventId and operationId.
  - Test endorsement with both deployed peers, not only the current single-peer OR path.

  Exit gate: the same proof produces identical read/write sets on both peers, duplicate delivery is safe, and API/Postgres/Fabric identifiers can be traced end to end.

  ### Phase 2: Replace Snapshot Persistence with Transactional Commands

  - Remove the in-memory engine as the authoritative runtime for PostgreSQL-backed operation.
  - Introduce command services and repositories that load and mutate only the affected rows.
  - Execute business updates, workflow transitions, domain events, and outbox insertion in one PostgreSQL transaction.
  - Eliminate runtime TRUNCATE and full-state rebuilds. Keep snapshot import/export only as explicit admin or test tooling.
  - Use row locks for stock, lot balances, allocations, and entitlements. Add version columns for optimistic concurrency where records can be edited independently.
  - Add unique idempotency keys to commands and outbox events.
  - Implement an outbox worker using FOR UPDATE SKIP LOCKED, bounded exponential retry, terminal DEAD_LETTER status, and manual retry support.
  - Expose proof states as PENDING, SUBMITTING, COMMITTED, and FAILED; Fabric failure must not roll back valid operational state but must be visible and actionable.
  - Make the worker independently runnable so API replicas do not each need an embedded poller.

  Exit gate: crash testing demonstrates no committed business operation can lose its outbox event, and concurrent API replicas cannot overwrite or double-spend stock or entitlement balances.

  ### Phase 3: Introduce Child-Lot Lineage and Conservation

  - Extend lots with rootLotId, parentLotId, originalQuantityKg, remainingQuantityKg, unit, and lifecycle status.
  - Represent each dispatch as a movement of a specific quantity from one source lot:
      - Lock the source lot.
      - Reject movement above its remaining quantity.
      - Reduce the parent’s remaining quantity.
      - Create a child lot for the dispatched quantity in IN_TRANSIT.
      - On receipt, move the child to RECEIVED and credit only the received quantity.

  - Represent shortage, damage, quality rejection, and transit loss as explicit quantity adjustments linked to the movement and investigation record. Quantities must never disappear only because an alert was
    raised.

  - For transformations, consume explicit input lot quantities and create output child lots with conversion yield and declared process loss.
  - Make stock positions a projection of lot balances by stakeholder, commodity, and lot. Do not use pooled stock to authorize a lot-specific movement.
  - Preserve integer kilograms for this cycle. Reject fractional and negative quantities.
  - Add a reconciliation service that verifies for each root lot:

  created = available + reserved + in transit + received downstream
          + distributed + declared loss

  Exit gate: oversize dispatch, concurrent dispatch, partial receipt, repeated receipt, transformation, allocation, distribution, and shortage scenarios all preserve quantity and lineage.

  ### Phase 4: Implement the Versioned Domain Workflow

  - Define workflow templates in code with a stable template ID and version.
  - Persist workflow instances, current state, transition history, command idempotency key, actor, timestamps, related entity IDs, and failure reason.
  - Centralize transition guards for:
      - Allowed source and destination states.
      - Required application roles.
      - Active stakeholder status.
      - Quantity availability.
      - Required authorization or receipt evidence.
      - Ledger-proof policy where applicable.

  - Use explicit states such as PENDING_AUTHORIZATION, AUTHORIZED, DISPATCHED, RECEIVED, RECEIVED_WITH_SHORTAGE, COMPLETED, REJECTED, and CANCELLED.
  - Do not discover authorization by scanning generic ledger events. Store authorization against the workflow instance and bind it to the authenticated actor.
  - Make every transition idempotent. Repeating the same command returns the existing result; conflicting reuse of an idempotency key returns 409.
  - Keep controllers thin and route all mutations through command/workflow services.
  - Add endpoint-level role metadata and enforce the procurement, godown, FPS, department, and auditor role matrix in the API.
  - Include the authenticated actor in every domain event and Fabric proof. For the two-org near-MVP, document that some logical application roles submit proofs through the department Fabric identity.

  Exit gate: invalid transitions and unauthorized roles are rejected consistently, workflow state survives restart, and retries cannot duplicate movements or distributions.

  ### Phase 5: API, UI, Audit, and Operations

  - Return additive operation/proof metadata from mutation endpoints:

  {
    data: T;
    operationId: string;
    idempotencyKey: string;
    proof: {
      eventId: string;
      status: 'PENDING' | 'SUBMITTING' | 'COMMITTED' | 'FAILED';
      fabricTxId?: string;
    };
  }

  - Accept Idempotency-Key on every mutation endpoint.
  - Add read endpoints for operation and proof status, including failure reason and retry state.
  - Update trace APIs to return root/parent/child lot lineage, movements, adjustments, workflow transitions, and committed Fabric proofs.
  - Update the UI to distinguish operational completion from ledger-proof status without blocking normal workflow on expected Fabric delay.
  - Add admin views and metrics for outbox depth, oldest pending age, failed proofs, retry count, workflow failures, quantity reconciliation failures, and Fabric connectivity.
  - Update bootstrap scripts to use explicit Fabric image versions, avoid destructive teardown by default, and provide separate reset and upgrade commands.
  - Validate chaincode package version and sequence before deployment and verify commit readiness on both organizations.

  Exit gate: happy path and exception path work through the UI, proof lag/failure is visible, reconciliation is clean, and the two-org stack can be rebuilt reproducibly.

  ## Public Interfaces and Schema

  - Add LedgerProof, ProofStatus, WorkflowTemplate, WorkflowInstance, WorkflowTransition, LotMovement, and QuantityAdjustment shared types.
  - Add child-lot lineage and remaining quantity fields to CommodityLot.
  - Add operation_id, idempotency_key, schema_version, retry scheduling, real Fabric transaction ID, and dead-letter metadata to the outbox/proof tables.
  - Add workflow instance and transition-history tables.
  - Add movement and quantity-adjustment tables with foreign keys to source and child lots.
  - Preserve existing endpoint paths. Mutation response changes are additive during this cycle.
  - Deprecate snapshot persistence and direct API-to-named-chaincode command replay; remove them only after compatibility tests and documentation are complete.

  ## Test Plan

  - Determinism: execute the same chaincode proposal on both peers and compare responses and write sets.
  - Atomicity: kill the process before commit, after business writes, and during Fabric submission; verify rollback or recoverable outbox state.
  - Concurrency: simultaneous dispatches, distributions, receipts, and outbox workers must not double-spend or duplicate.
  - Conservation: full, partial, short, rejected, transformed, allocated, and distributed lot paths must balance exactly.
  - Workflow: test every allowed transition, invalid transition, role denial, restart recovery, idempotent retry, and conflicting idempotency key.
  - Fabric: duplicate proof, conflicting proof, peer outage, orderer outage, retry recovery, dead-letter, and real transaction-ID correlation.
  - Security/privacy: ensure no raw beneficiary identity, OTP, biometric, mobile number, or complete ration-card value enters proofs or logs.
  - Regression: preserve demo workflow, dashboards, trace views, fixture generation, and scripted happy/exception paths.
  - Release commands: npm run build, npm run typecheck, npm run lint, npm test, demo smoke, and live two-peer Fabric regression.

  ## Demo Assumptions and Future Todos

  Capture these in assumptions-for-demo.md:

  - PostgreSQL is the operational source of truth; Fabric proof completion is eventually consistent.
  - The deployed network has two organizations and is a governance simulation, not the final consortium.
  - Application roles are enforced by the API; not every logical role has an independent Fabric MSP in this cycle.
  - Static development tokens and generated development crypto are permitted only in local/demo environments.
  - Quantities use integer kilograms; unit conversion and calibrated weighbridge integration are deferred.
  - Existing local transactional data is reset and reseeded during migration.
  - One district and modest transaction volume are assumed.
  - Single-node components are accepted for local demonstration, with backup and recovery limited to documented reset/reseed procedures.

  Capture these as production-readiness todos:

  - Deploy Procurement, FPS, and Audit organizations and define production endorsement/private-data policies.
  - Introduce real OIDC/IAM, organization-scoped Fabric identities, certificate enrollment, revocation, and HSM-backed keys.
  - Add multi-node Raft, redundant peers, Kubernetes deployment, persistent-volume backup, disaster recovery, and zero-downtime chaincode upgrades.
  - Add decimal units, weighbridge evidence, quality inspection, multi-source transformations, returns, and reversal workflows.
  - Add schema migration tooling and preservation of pilot/production transactional data.
  - Add event signing, key rotation, secrets management, SIEM integration, alerting SLOs, retention rules, and privacy-impact review.
  - Add SMART-PDS, ePoS, authentication, logistics, and external reconciliation adapters.
  - Conduct load, failover, penetration, privacy, and formal quantity-invariant testing before pilot production.

  ## Completion Criteria

  The near-MVP is complete only when all critical and high findings are implemented, tests are green, two-peer Fabric endorsement is deterministic, every operational mutation atomically creates an outbox
  event, quantities reconcile through child-lot lineage, workflow transitions are durable and role-controlled, and all remaining limitations are explicitly recorded in the assumptions and production-readiness
  documents.
